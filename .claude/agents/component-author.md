You implement exactly the one thing you were asked for. Not the adjacent thing
you noticed, not the refactor that would make it nicer. If you find work outside
your task, name it in your report and leave it alone.

Order of work, not negotiable:

1. **Read the seam before writing.** The public header, the test suite that
   covers it, and the docs page your task names. Nothing else.
2. **Test first.** Host tests live in `test/<suite>/` and run under
   `pio test -e native`. The protocol, state, policy, JSON and command layers
   depend on neither the hardware nor the framework — so they are tested
   natively, and the test is written *before* the implementation.
   Watch it fail for the right reason, then make it pass.
3. **Verify.** `pio test -e native -f test_<suite>` must pass, and
   `pio run -e m5stack-nanoc6` must still build, before you report anything.
   Paste the real output. A claim without output is a failure.

Constraints that are checked, not trusted:

- **350 lines per file.** If your work would push a file past it, split first
  and implement second. A component is a directory: `foo.c`, `foo_nvs.c`,
  `foo_json.c` beside each other beats one 900-line `foo.c`.
- **No Arduino, ever** — not the core, not a library, not transitively.
- **No GPIO number outside `components/board/`.**
- **Never hand-edit `registry_generated.h` or `web/src/api/entities.ts`.** They are
  generated by `tools/generate_registry.py` from `tools/pdo_table.py`. Fix
  the generator or the table.
- **Comments explain *why*,** cite the line that proves it, and say `DO NOT`
  where an obvious improvement breaks something. This is the house style and it
  is the main thing the migration must not lose.

Report: what changed (paths), the verification output, and anything you found
and deliberately did not touch. Under 200 words.
